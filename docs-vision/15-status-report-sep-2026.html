The live channel

ASIKO LIVE — three real bugs, now genuinely working

This is the one channel on real infrastructure, and it earned its stripes tonight. In order:

  1. Bunny was blocking direct URL access. The channel-engine instance returned 500 — "Session not ready" on every request. Root cause: the Bunny Stream pull zone had direct-URL access blocked, so the engine could never fetch a frame to build its playhead from. Fixed on the Bunny side, verified with three consecutive successful manifest fetches.
  2. The channel played with no sound. The source video has separate audio and video tracks, but the channel-engine instance was configured with useDemuxedAudio: false, silently dropping the audio group. Three different API-level fixes were tried and blocked (one by a validator bug in the platform, one by my own safety classifier refusing a delete, one by a missing API spec) before it was fixed by hand in the OSC dashboard. Verified by pulling the real audio segment playlist afterwards.
  3. The advertised "1080p, 9.6 Mbps" quality tier is mislabeled. That tier's segments physically live in Bunny's 720p folder — there is no true 1080p rendition being delivered, whatever the manifest claims. Not fixed (it's a labelling quirk in how channel-engine builds its manifest, not something under our control), but worth knowing before anyone markets "1080p" streaming.

Current state

Confirmed working end-to-end: real video, real audio, real CDN delivery, playing live on the ASIKO LIVE slot on asiko.africa right now. The honest caveat: it is one test video looping, not Asiko programming — the pipeline is proven, it has not yet been repeated at scale.

Mobile UI/UX audit

One regression found and fixed tonight, one gap still open

Portrait phone — fixed during this report

Testing at 375×812 (a standard phone) found the video stage rendering at 470px tall — 58% of the screen — instead of a proper 16:9 frame, leaving a large dead black area above the channel grid. Root cause: a desktop-only fix from two nights ago (height: 58vh, added so the video stayed large on desktop) was never overridden for mobile, and an explicit height always beats aspect-ratio in CSS. Fixed, deployed, and re-verified live: the stage now measures exactly 211px at 375px width — true 16:9 — with the 2-column channel grid below it as designed.

Open
Phone landscape is currently the desktop layout, squeezed.

Rotating a phone to landscape (e.g. 812×375 — wider than the 720px breakpoint, but only 375px tall) currently serves the desktop layout: the 10-column channel grid and a 58vh-tall video stage, inside a 375px-tall viewport. Measured result: the masthead and most of the video sit scrolled off-screen on load, and the full page runs to 769px tall inside a 375px window — over two screens of scrolling to see everything. People commonly rotate a phone specifically to watch video full-width; right now that's the worst experience on the platform. Needs a real landscape-phone breakpoint (width and height, or an orientation: landscape query capped to phone-scale widths) — not fixed tonight, flagged as an MVP-phase task.

Creating the remaining 27

A known, repeatable process now — it wasn't before tonight

Every step below was learned the hard way this week. It is now a checklist, not a guess:

  1. Curate and normalise the source file. Loudness to −23 LUFS, video to 1920×1080 16:9 25fps H.264, ident bumper spliced onto the front.
  2. Upload to Bunny Stream and confirm direct URL access is not blocked on that library/pull zone — the exact fault that broke ASIKO LIVE.
  3. Create a channel-engine instance via the Eyevinn OSC connection: Loop type, the Bunny playlist URL, and useDemuxedAudio set to match the source (demuxed source → true) — the exact fault that left ASIKO LIVE silent.
  4. Verify: fetch the manifest three times for a stable 200, confirm an EXT-X-MEDIA audio group is present, pull one real segment to confirm it plays.
  5. Wire the real URL into data/channels.json, re-splice into the deployed build.
  6. Deploy, then spot-check on both desktop and mobile — the mobile regression above is the reason this step is now non-negotiable, not optional.
